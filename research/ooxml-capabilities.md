# Question
Which HTML/CSS constructs have a faithful native PresentationML/DrawingML representation, and which do not?

# Findings

Legend:
- **Native** = direct OOXML construct, no rasterization required.
- **Partial** = OOXML has a direct construct, but only a subset or approximation of CSS semantics is expressible.
- **Raster-only** = no faithful PresentationML/DrawingML construct; the visual must be baked into an image.

| CSS / HTML construct | Verdict | Native PresentationML / DrawingML mapping | Evidence and caveats |
|---|---|---|---|
| Text runs | Native | `a:r`, `a:rPr`, `a:endParaRPr` | Run-level styling is directly modeled in DrawingML. Office resolves missing values through inheritance. `rPr` covers text-run properties such as kerning, baseline, size, caps, and proofing. [MS-OI29500 §21.1.2.3.9 rPr](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oi29500/953e072c-f234-4373-b017-3f1f71eac93b) |
| Paragraph properties | Native | `a:pPr` | Paragraph alignment, indentation, bullets, tabs, spacing-before/after, and list-level inheritance are all native in the paragraph-properties model. [MS-OI29500 §21.1.2.2.7 pPr](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oi29500/3bf4b4b9-d1cd-4610-be56-9427e22c5fb4) |
| Line spacing | Native | `a:lnSpc` with `a:spcPct` or `a:spcPts` | Office documents `lnSpc` as line spacing inside a paragraph; it accepts both percentage and point-based spacing. [MS-OI29500 §21.1.2.2.5 lnSpc](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oi29500/4e043105-2ae4-4b85-baa8-4324ca7a6367) |
| Box insets / padding | Native | `a:bodyPr@lIns/tIns/rIns/bIns` | Text box insets are explicit body properties. Office treats them as internal margins, with documented defaults when omitted. [MS-OI29500 §21.1.2.1.1 bodyPr](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oi29500/b3da041f-d56f-464b-a9b3-2e3274de9caf), [BodyProperties.LeftInset](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.bodyproperties.leftinset?view=openxml-3.0.1), [BodyProperties.TopInset](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.bodyproperties.topinset?view=openxml-3.0.1) |
| Autofit | Partial | `a:noAutofit`, `a:normAutofit`, `a:spAutoFit` | The XML model is native, but Office’s actual fit behavior is not a single CSS-style algorithm. `normAutofit` scales text to keep it inside the shape; `spAutoFit` resizes the shape; `noAutofit` disables fitting. [MS-OI29500 §21.1.2.1.2 noAutofit](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oi29500/56ab6d15-2c9a-4d77-bc6b-3d8a7d98ebf3), [MS-OI29500 §21.1.2.1.3 normAutofit](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oi29500/d39a4528-75c3-4542-88aa-db874e68085c), [MS-OE376 §5.1.5.1.4 spAutoFit](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oe376/19d31037-28bf-4693-85be-3a37bfe82d51) |
| Solid fill | Native | `a:solidFill` + color transforms | Solid fills are first-class shape fill properties. Per-color alpha is native via `a:alpha`. [MS-OI29500 §20.1.8 Shape, Fills, Effects and Line Properties](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oi29500/c0c046ec-a61d-405d-88fe-74d8487a37d7), [SolidFill](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.solidfill?view=openxml-3.0.1), [Alpha](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.alpha?view=openxml-3.0.1) |
| Gradient fill | Partial | `a:gradFill` with `a:lin` or `a:path` | Linear gradients are direct; path gradients exist but are shape-bounding-box based rather than CSS radial-gradient semantics, and repeating/conic gradient behavior is not a native DrawingML primitive. [MS-OI29500 §20.1.8 Shape, Fills, Effects and Line Properties](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oi29500/c0c046ec-a61d-405d-88fe-74d8487a37d7), [GradientFill](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.gradientfill?view=openxml-3.0.1), [PathGradientFill](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.pathgradientfill?view=openxml-3.0.1) |
| Pattern fill | Partial | `a:pattFill` | DrawingML pattern fills are a fixed preset catalog with foreground/background colors, so they cover common hatch/texture looks but not arbitrary CSS patterns or image-based patterns without rasterizing the pattern asset. [MS-OI29500 §20.1.8 Shape, Fills, Effects and Line Properties](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oi29500/c0c046ec-a61d-405d-88fe-74d8487a37d7), [PatternFill](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.patternfill?view=openxml-3.0.1), [PresetPatternValues](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.presetpatternvalues?view=openxml-3.0.1) |
| Borders | Partial | `a:ln` on shapes; `a:lnL/a:lnR/a:lnT/a:lnB` on table cells | A single shape outline is native. CSS-style independent per-side borders are only native for DrawingML table cells, not for a generic autoshape with one stroke. [MS-OI29500 §20.1.2.2.24 ln](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oi29500/5564035f-88ff-4ab8-bbfb-d2998a83324d), [MS-OE376 §5.1.6.11 tbl](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oe376/6c3a6294-ed13-479a-871a-7e094963289e), [MS-OE376 §5.1.6.14 tc](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oe376/de4562ba-7901-48df-9803-414ded131f2b) |
| Corner radius | Partial | `a:prstGeom prst="roundRect"` or `a:custGeom` | There is no standalone CSS-like per-corner radius property. PowerPoint expresses rounded corners by choosing a rounded-rectangle preset geometry or by defining a custom path geometry. [PresetGeometry](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.presetgeometry?view=openxml-3.0.1), [ShapeTypeValues.RoundRectangle](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.shapetypevalues?view=openxml-3.0.1), [CustomGeometry](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.customgeometry?view=openxml-3.0.1) |
| Shadows / blur / opacity | Partial | `outerShdw`, `innerShdw`, `blur`, `softEdge`, `a:alpha` | DrawingML can represent common shadow and blur effects, and color alpha gives transparency. But CSS-style multi-layer shadows, spread radius, and element-wide compositing opacity are not a single 1:1 OOXML property. [MS-OE376 §6.1.2.18 shadow](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oe376/471d7074-ce70-42ab-8202-d0243f2866f2), [MS-OE376 §5.1.10.15 blur](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oe376/854057ba-87f2-4715-9ae4-dba09f5cce68), [MS-OE376 §5.1.10.53 softEdge](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oe376/c0a0b439-a2e0-4cf1-8289-368ee27fa113), [Alpha](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.alpha?view=openxml-3.0.1) |
| Images and cropping | Native | `p:pic` + `p:blipFill` + `a:srcRect` | Pictures are native PowerPoint objects. Rectangular crop is directly expressed by `srcRect`; Office documents it as a source rectangle within picture fill. [Picture](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.presentation.picture?view=openxml-3.0.1), [MS-OE376 §5.8.2.2 blipFill](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oe376/5e71ccac-785c-4553-8637-7c00ecc06f3a), [MS-OE376 §5.1.10.55 srcRect](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oe376/7fb94eed-d199-410e-8f43-bc29ed962263) |
| Tables | Native | `a:tbl`, `a:tc`, `gridSpan`, `rowSpan`, `lnL/lnR/lnT/lnB` | DrawingML tables are native slide objects. Office supports merged cells, table grids, and per-cell borders. [MS-OE376 §5.1.6.11 tbl](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oe376/6c3a6294-ed13-479a-871a-7e094963289e), [MS-OE376 §5.1.6.14 tc](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oe376/de4562ba-7901-48df-9803-414ded131f2b) |
| SVG / vector shapes | Native | `a:custGeom` for freeform vectors; `asvg:svgBlip` for SVG images | Modern PowerPoint can carry actual SVG as a DrawingML extension and can also define true vector shapes with custom geometry paths. [CustomGeometry](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.customgeometry?view=openxml-3.0.1), [MS-ODRAWXML svgBlip](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-odrawxml/2451f45e-5d77-4661-86d1-0a017fced779), [MS-ODRAWXML CT_SVGBlip](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-odrawxml/68e0150d-6a01-4ba5-ac4d-5a18d685229b) |
| z-order | Native | `p:spTree` child order | Slide stacking order is the order of shape-based objects in the shape tree: backmost first, frontmost last. PowerPoint’s object model documents the same convention. [ShapeTree](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.presentation.shapetree?view=openxml-3.0.1), [Shape.ZOrderPosition](https://learn.microsoft.com/en-us/office/vba/api/powerpoint.shape.zorderposition) |
| Clipping | Partial | `a:srcRect` for rectangular crop; `a:prstGeom` / `a:custGeom` for geometry-bound masking; `o:clippath` is legacy VML only | PowerPoint has no general DrawingML `clipPath` element. You can crop bitmap sources or constrain content to a shape geometry, but arbitrary CSS clip-path semantics are not natively exposed in PresentationML. [MS-OE376 §5.1.10.55 srcRect](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oe376/7fb94eed-d199-410e-8f43-bc29ed962263), [PresetGeometry](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.presetgeometry?view=openxml-3.0.1), [CustomGeometry](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.customgeometry?view=openxml-3.0.1), [ClipPath](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.vml.office.clippath?view=openxml-3.0.1) |

# Recommendation
Prefer native PresentationML/DrawingML whenever the construct maps directly, because editability is a hard requirement. In practice:
- Keep text, paragraph layout, fills, tables, images, vector shapes, and z-order native.
- Use native geometry for rounded corners only when a single preset/custom path is acceptable.
- Treat autofit, gradients, pattern fills, borders, shadows/blur/opacity, and clipping as partial mappings that may need approximation logic.
- Rasterize only the CSS cases that have no faithful OOXML shape-level equivalent, especially repeating/conic gradients and clip-path scenarios that cannot be reduced to image crop or shape geometry.

# Open questions
None about core expressibility. The remaining decisions are converter policy choices, not missing OOXML primitives.
